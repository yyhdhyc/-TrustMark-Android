# v1.2 payload 位布局

本文件描述应用在 TrustMark 二进制 payload 内部定义的帧格式。它位于 BCH 纠错层**之内**，不是 TrustMark 的 100 位 packet 格式。

## 1. 两层结构

```text
通用文本 或 批次短码 + 编号
      │  PayloadCodec (Kotlin)
      ▼
v1.2 frame（通用 6 + L×5/6 位；批次固定 40 位，<= 40/61/68/75）
      │  trustmark::Bits::apply_error_correction_and_schema (Rust)
      ▼
100-bit packet = data（补零到容量） + BCH parity + schema(4)
      │  encoder_Q.onnx
      ▼
水印图片
```

解码时反向：

```text
100-bit decoder output
      │  BCH 校验/纠错，读取最后 2 位 schema
      ▼
data 位（40/61/68/75，尾部有零填充）
      │  PayloadCodec.decode（按 bit 0 分流）
      ▼
通用文本 或 批次短码 + 编号 + CRC 结果
```

## 2. 通用模式帧

通用模式**没有编号字段**，也没有份数或映射表概念。

| 字段 | 位宽 | 说明 |
| --- | ---: | --- |
| 帧类型 | 1 | 固定 `0` |
| 字母表模式 | 1 | `0` = A–Z（5 位/字符）；`1` = 扩展字母表（6 位/字符） |
| 文本长度 | 4 | `1..15`；`0` 保留为非法 |
| 文本 | L × 5/6 | 见字母表 |

固定头 = 1 + 1 + 4 = **6 位**。

```text
bit 0      : 帧类型 = 0
bit 1      : 字母表模式
bit 2..5   : 文本长度 L
bit 6..    : 文本位串
```

### 5-bit 字母表

`A=0, B=1, ..., Z=25`

只有文本全部为 A–Z 时才使用。

### 6-bit 字母表

```text
0..25   A..Z
26..35  0..9
36      -
37      _
38      .
39      (space)
```

出现数字、空格或 `- _ .` 时使用。6 位模式每字符多 1 位，容量会下降。

### 容量公式

```text
total = 6 + L * bitsPerChar
valid = total <= ecc.dataBits
remaining = ecc.dataBits - total
```

| BCH 等级 | 数据容量 | 5 位文本上限 | 6 位文本上限 |
| --- | ---: | ---: | ---: |
| `BCH_SUPER` | 40 | 6 字符 | 5 字符 |
| `BCH_5` | 61 | 11 字符 | 9 字符 |
| `BCH_4` | 68 | 12 字符 | 10 字符 |
| `BCH_3` | 75 | 13 字符 | 11 字符 |

示例：`ACME` 使用 5 位模式，总长为 `6 + 4 × 5 = 26` 位：

```text
type     0
alphabet 0
length   0100        (4)
text     00000 00010 01100 00100   (A C M E)
```

## 3. 批次溯源模式帧

批次模式**只有批次短码、编号和 CRC**，没有文本。

| 字段 | 位宽 | 说明 |
| --- | ---: | --- |
| 帧类型 | 1 | 固定 `1` |
| 批次短码 | 20 | 4 个字母，每个 5 位 |
| 编号 | 12 | `1..4095`，`0` 保留 |
| CRC-7 | 7 | 对前 33 位计算 |
| **合计** | **40** | 正好等于 BCH Super 数据容量 |

```text
bit 0       : 帧类型 = 1
bit 1..20   : 批次短码，4 × 5 位
bit 21..32  : 12 位编号
bit 33..39  : CRC-7
```

### 批次短码

- 固定 4 个 ASCII 大写字母。
- 每个字母映射为 5 位：`A=0`，`B=1`，……，`Z=25`。
- 值 `26..31` 为非法编码，解析时直接判定帧无效。
- 可用空间：`26^4 = 456,976` 个短码。
- 不再使用 v1.1 的数字、`B` 前缀或 `G` 时间戳格式。

### 12 位编号

- 单批次编号范围 `1..4095`。
- `0` 保留为非法值。
- 单批次最多 4095 个接收人/输出；建表、补表和生成前都会校验。

### CRC-7/MMC 参数

| 参数 | 值 |
|---|---|
| 宽度 | 7 |
| 多项式 | `0x09`（`x^7 + x^3 + 1`） |
| 初始值 | `0x00` |
| 输入反射 | 否 |
| 输出反射 | 否 |
| 结果异或 | `0x00` |
| 校验范围 | 前 33 位：帧类型 + 批次短码 + 编号 |

计算时采用标准 8 位寄存器形式（隐式 `x^7` 项，末尾补 7 个零），取低 7 位余数；`123456789` 的 ASCII 位串校验值应为 `0x75`。解码时重新计算前 33 位的 CRC，并与后 7 位比较。

CRC 失败时直接返回：

```text
解码失败
```

不得把 CRC 失败的结果交给映射表查询，也不得显示为“无匹配”。

### 批次帧示例

`ABCD`，编号 42：

```text
type     1
code     00000 00001 00010 00011   (A B C D)
serial   000000101010              (42)
CRC-7    1000110                   (0x46)
```

完整 40 位：

```text
1000000000100010000110000001010101000110
```

## 4. 解码分流与兼容性

- `PayloadCodec.decode` 只看 bit 0：`0` 走通用帧，`1` 走批次帧。
- 通用帧：长度必须为 1..15，字符 code 必须在对应字母表内，否则失败。
- 批次帧：至少 40 位；CRC 必须匹配；短码 4 个字母；编号 1..4095。
- 不再回退到 7-bit/8-bit ASCII，也不把任意二进制当作文本展示。
- v1.1 的 TMK2 帧以 `101` 开头，会被当作批次帧并因 CRC 失败而拒绝，这是有意的不兼容行为。
- 批次帧 CRC 通过后，`DecodeWorker` 自动查询 `BatchStore`；查询结果只影响展示颜色，不改变 payload 有效性。

## 5. 为什么不用 TrustMark 的“文本模式”

Adobe 的 Rust crate 明确说明 text mode 未实现；Python 的 `encode_text_ascii` 使用 7-bit ASCII 且没有文本长度字段，解码时只能靠 `rstrip('\x00')`，无法可靠还原编号，也无法判断 padding。v1.2 在 BCH 预算内显式加入帧类型、长度和 CRC，因此跨设备可逆，并能区分“通用文本”和“批次溯源”。

## 6. 安全边界

payload 编码不是加密，也不是签名。任何知道格式的人都能伪造同样格式的 payload；需要真实性/来源证明时，应结合 C2PA 或数字签名。批次映射表只保存在本机加密存储中，卸载应用会丢失，必须定期导出备份。
